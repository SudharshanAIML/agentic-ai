1. Tool calling is structured communication

Suppose we have:

def get_balance(account_id: int):
    return 50000

A human understands:

"This function takes an account ID and returns a balance."

But the LLM needs a machine-readable description.

So the function becomes a tool definition.

Conceptually:

{
  "name": "get_balance",
  "description": "Get the current account balance for an account.",
  "parameters": {
    "type": "object",
    "properties": {
      "account_id": {
        "type": "integer",
        "description": "The customer's account ID."
      }
    },
    "required": ["account_id"]
  }
}

This is essentially a contract between the model and the tool runtime.

2. Tool schema

A tool schema answers four questions:

What is the tool called?
What does it do?
What inputs does it accept?
Which inputs are mandatory?

For example:

Tool name:
get_balance


Description:
Get the current balance for an account.


Input:
account_id → integer


Required:
account_id

Think of it as an API specification for the LLM.

3. Function signature → schema

Python:

def get_balance(account_id: int) -> float:
    """Get the current balance for an account."""

can be represented as:

{
  "name": "get_balance",
  "description": "Get the current balance for an account.",
  "parameters": {
    "type": "object",
    "properties": {
      "account_id": {
        "type": "integer"
      }
    },
    "required": ["account_id"]
  }
}

Notice:

Python                       Schema


get_balance             →    name
docstring               →    description
account_id              →    property
int                     →    integer
required argument       →    required

This is why type annotations and descriptions matter so much when creating tools.

4. Why JSON?

Because the communication between the model and runtime needs to be structured.

Instead of the model generating:

Hey, please call the get_balance function
with account ID 123.

it can produce a structured tool call:

{
  "name": "get_balance",
  "arguments": {
    "account_id": 123
  }
}

Now the runtime doesn't need to guess what the model meant.

It can directly do:

tool_name = "get_balance"
arguments = {
    "account_id": 123
}

and then:

get_balance(account_id=123)
5. The complete tool-calling flow

Let's slow this down.

User says:

"What is the balance of account 123?"

Step 1 — Runtime provides tools to the LLM
LLM receives:


Tool:
get_balance


Description:
Get the current balance for an account.


Parameters:
account_id: integer
Step 2 — LLM interprets the request

User:

"What is the balance of account 123?"

The LLM determines:

Relevant capability:
get_balance


Argument:
account_id = 123
Step 3 — LLM generates a tool call

Conceptually:

{
  "name": "get_balance",
  "arguments": {
    "account_id": 123
  }
}

Important:

The LLM has NOT executed the function.

It has only requested:

"Runtime, please execute this."

6. Runtime receives the tool call

The agent runtime sees:

tool = get_balance
arguments = {
    account_id: 123
}

Then it looks up the actual implementation:

tools = {
    "get_balance": get_balance
}

and executes:

result = tools["get_balance"](account_id=123)

Result:

50000
7. Tool result goes back to the LLM

This is the next critical step.

The runtime now tells the LLM:

Tool:
get_balance


Result:
50000

The LLM can now use that information.

So:

User
 ↓
LLM
 ↓
Tool Call
 ↓
Runtime
 ↓
Tool
 ↓
Tool Result
 ↓
LLM
8. Tool call vs tool result

Keep these two concepts separate.

Tool call

Generated by the model:

{
  "name": "get_balance",
  "arguments": {
    "account_id": 123
  }
}
Tool result

Generated by the tool:

50000

So:

LLM → Tool Call


Tool → Tool Result

Very important.

9. Messages

Modern tool-calling systems usually represent this interaction using messages.

Conceptually:

HumanMessage
     ↓
AIMessage
     ↓
ToolMessage
     ↓
AIMessage

For example:

Human
"What is my balance?"
AI
Tool call:
get_balance(account_id=123)
Tool
50000
AI
"Your balance is ₹50,000."

So the conversation can be thought of as:

┌──────────────┐
│ HumanMessage │
└──────┬───────┘
       ↓
┌──────────────┐
│  AIMessage   │
│ tool_call    │
└──────┬───────┘
       ↓
┌──────────────┐
│ ToolMessage  │
│ result       │
└──────┬───────┘
       ↓
┌──────────────┐
│  AIMessage   │
│ final answer │
└──────────────┘

This becomes extremely important in LangGraph.

10. Why does the ToolMessage need to exist?

Suppose the LLM requested:

get_balance(123)

and the runtime simply calculated:

50000

but didn't send that result back to the LLM.

The model wouldn't know what happened.

So we need:

AI:
"Call get_balance"


Tool:
"Here is the result: 50000"


AI:
"Okay, now I can answer."

That's the basic message protocol.

11. Multiple tools

Now suppose we have:

def get_balance(account_id: int):
    ...


def get_transactions(account_id: int):
    ...


def calculate_average(values: list[float]):
    ...

Their schemas might look like:

get_balance
    account_id: integer


get_transactions
    account_id: integer


calculate_average
    values: array[number]

The LLM receives all three.

User:

"What is my average transaction?"

The LLM recognizes:

calculate_average

but asks:

"Where do I get values?"

It doesn't have them.

So it first calls:

get_transactions(123)
12. Now watch the message sequence

User:

"What is my average transaction?"

LLM:

Tool call:
get_transactions(123)

Tool:

[
  500,
  1200,
  800,
  2000,
  1500
]

LLM receives the result.

Now it has:

values =
[500,1200,800,2000,1500]

It can call:

calculate_average(
    [500,1200,800,2000,1500]
)

Tool:

1200

LLM:

"Your average transaction amount is ₹1,200."

14. Let's introduce tool_call_id

There is another subtle concept.

Imagine the model calls:

get_balance(123)

The runtime needs to associate the result with that specific request.

So tool calls typically have an ID:

{
  "id": "call_abc123",
  "name": "get_balance",
  "arguments": {
    "account_id": 123
  }
}

The result can correspond to:

{
  "tool_call_id": "call_abc123",
  "result": 50000
}

This becomes especially important when:

multiple tools are called
tools execute in parallel
there are multiple tool calls in one model response
15. Parallel tool calls

Suppose the user says:

"Get my balance and my last transactions."

These two operations are independent.

The LLM could request:

get_balance(123)


get_transactions(123)

Potentially both can execute concurrently.

Conceptually:

                    LLM
                     │
             ┌───────┴────────┐
             ↓                ↓
       get_balance      get_transactions
             │                │
             ↓                ↓
          ₹50,000         transactions
             │                │
             └───────┬────────┘
                     ↓
                    LLM

This is one of the places where agent orchestration becomes more interesting.

LangGraph can model such execution patterns explicitly.

16. Structured arguments

Consider:

def search_products(
    category: str,
    min_price: float,
    max_price: float,
    limit: int
):
    ...

The LLM could produce:

{
  "name": "search_products",
  "arguments": {
    "category": "laptop",
    "min_price": 50000,
    "max_price": 100000,
    "limit": 10
  }
}

The runtime can validate:

category → string ✓
min_price → number ✓
max_price → number ✓
limit → integer ✓

This is why schemas are important for reliability.

17. What if the model generates invalid arguments?

Suppose:

{
  "name": "get_balance",
  "arguments": {
    "account_id": "hello"
  }
}

But our schema says:

account_id: integer

The runtime can reject it.

Possible flow:

LLM
 ↓
Invalid tool call
 ↓
Validation
 ↓
Error
 ↓
LLM / retry / terminate

This is one reason tools shouldn't simply accept arbitrary strings.

18. Good vs bad tool design
Bad
def execute(operation: str):
    ...

Potentially:

execute("delete everything")

Very broad capability.

Better
def get_customer(customer_id: int):
    ...


def get_customer_orders(customer_id: int):
    ...


def update_customer_email(
    customer_id: int,
    email: str
):
    ...

Each capability is explicit.

This gives the LLM a much clearer action space.

19. This leads to a major principle

An agent is only as reliable as the interfaces you expose to it.

If you expose:

run_any_sql(query)
execute_shell(command)
call_any_api(url)

you've given the agent enormous uncontrolled power.

If instead you expose:

get_customer()
get_orders()
get_invoice()
search_products()

the action space becomes much more constrained.

This principle will become very important when we build MCP servers.

20. Now connect this to LangChain

LangChain gives us a convenient abstraction.

Instead of manually defining all the schema metadata, we can do:

from langchain.tools import tool


@tool
def get_balance(account_id: int) -> float:
    """Get the current balance for an account."""
    return 50000.0

LangChain can derive the tool schema from:

function name
+
type annotations
+
docstring

Conceptually:

Python Function
      │
      ▼
LangChain @tool
      │
      ▼
Tool object
      │
      ├── name
      ├── description
      └── args schema

Then a compatible chat model can be given those tools.

21. But don't jump into create_agent() yet

I want you to understand one more layer first.

There are actually three different things:

1. Tool definition
2. Tool binding
3. Agent execution
Tool definition
@tool
def add(a: int, b: int):
    ...
Tool binding

Conceptually:

model_with_tools = model.bind_tools([add])

This means:

"Model, these are the capabilities available to you."

Agent execution

Then something needs to perform:

LLM
 ↓
tool call
 ↓
execute tool
 ↓
tool result
 ↓
LLM

That's where agent orchestration comes in.

22. The crucial distinction: Binding ≠ execution

This is a common beginner mistake.

If you do:

model.bind_tools([add])

you have not created an agent loop.

You've basically told the model:

"You are allowed to request this tool."

The model may respond with a tool call.

But something still needs to:

receive tool call
       ↓
execute tool
       ↓
send result back
       ↓
call model again

That "something" is the runtime/agent orchestration.

And this is exactly where LangGraph becomes important.

24. One final concept for this lesson: Observation

Earlier we said:

Reason → Action → Observation

Now you can map it to actual mechanics:

Reason
  ↓
LLM decides tool
  ↓
Action
  ↓
Runtime executes tool
  ↓
Observation
  ↓
Tool result becomes context/message
  ↓
LLM

So "observation" isn't some magical thing.

It's essentially:

the information returned by an executed tool and made available to the model.

That's a much more useful engineering understanding.
